# Authoring a task file

How a drafting agent turns one backlog item into a task file that a builder agent can run. Read it together with `CLAUDE.md`, `AGENTS.md` and `docs/tasks/TEMPLATE.md`. The template says what a task file contains; this file says how to produce one, and what the drafter may and may not do.

A task file is the builder's whole brief and the verifier's whole checklist. The builder and verifier run in separate sessions that never saw your conversation with the user. Whatever you and the user decide must end up written in the file, or it is lost.

## The role

Role: **Drafter**. One drafting session runs at a time, and it drafts one task at a time. The user is present and answers questions; this is an interactive session, not an unattended one.

You may create or change these files only:

- `docs/tasks/<slug>.md`, the task file you are drafting (one per task in the session).
- `docs/tasks/backlog.md`, to remove the line (or table row) of each item you draft, in the same commit as its task file, and to add a line for any part you leave out (see "Backlog").

You may not change anything else: no code, no tests, no `openapi.yaml`, no `docs/requirements.md`, no `docs/api.md`, no `STACK.md`, no `CONVENTIONS.md`, no other task file, no scripts, no `Makefile`. If a task needs one of those changed first, you do not draft around it. You tell the user what change is needed and why, and stop. The user decides the edit (the contract especially: everything is generated from it, so it is changed deliberately, then regenerated by the user), makes it, and merges it before the task is run. The task file then states it as a **Prerequisite** that the builder checks, as `backend-hardening.md` and `mobile-drawer.md` do.

Work on the branch the session gives you. Commit in small steps, one commit per task (its task file and its backlog change together), and push that branch. Never push to `main`; the user merges. The task files must be on `main` before `scripts/stage.sh` can run them, so say that at the end.

## The user's rules while drafting

These come from how the user works. They apply to every drafting session.

- **Do not edit a `.md` file while a discussion is open.** Edit only after the user has made clear that the scope is settled, or after you asked and they confirmed. Explaining and asking are always fine.
- **Scope fully before writing, and ask rather than guess.** If a decision changes what gets built, ask. If it does not (naming, wording, an ordinary default), settle it yourself and list it afterwards.
- **Do not jump ahead.** Draft only the tasks in the plan the user approved, in that order, one at a time. Do not draft anything else, rewrite other files, or fix things you noticed on the way; add a line to the backlog or tell the user.
- **When the user asks you to explain something first, explain first.** No edits until they say so.
- Do not show diffs in the chat; the user reads them in their editor.

## Phase 0: choosing what to draft

A session starts here, not with a named backlog item (unless the user names one, in which case confirm it still fits the plan below and go to step 1). Nothing is edited in this phase, including the backlog.

1. **Read the whole backlog**, then `scripts/status.sh` (what is drafted, ready, built, verified, merged), the open task files, and `STACK.md`. Read all of it, every time; the order depends on all of it, and it changes whenever something merges.
2. **Reconcile the backlog with the facts before you trust it.** The backlog is a to-do list, not evidence of what exists. When sources disagree, believe them in this order: the code on `main`, then `openapi.yaml`, then the task reports and `scripts/status.sh`, then the backlog. Check at least:
   - the operations still unbuilt against `backend/internal/handler/stubs.go` and `openapi.yaml`, and the count in the backlog's state line;
   - every merged task's report: each Non-blocking finding is in the backlog (as a loose end, or as a fix-round line) or was fixed;
   - items whose task has since merged or been drafted, and any line in `STACK.md`, `docs/api.md` or the backlog that describes work as pending when it is done;
   - the dependencies between items: a front-end item that needs a back-end operation names it, and a back-end item that a front-end item waits on says so;
   - decisions the user made in conversation that are written nowhere (for example "after the app is finished", an ordering rule, something deliberately left out).

   Report every disagreement to the user in the plan (step 4), with what the source says and what the backlog says, and propose the fix. Do not change the backlog or any other doc yet: edits wait for the user's go-ahead (the rules above). Mechanical corrections the user approves are made in the same commit as the task they belong to, or in a commit of their own if no task is drafted.
3. **Work out the order with parallel work in mind.** The user runs a backend task and a frontend task at the same time whenever the files allow it, so the plan is a set of lanes, not a single list. For every candidate, find:
   - **Prerequisites:** what must be merged first (a backend slice before its frontend slice; the search API before the search UI; a contract or `STACK.md` change the user must make).
   - **Conflicts:** what it shares with tasks that are running or that you plan alongside it. Backend tasks that change the same `handler/` files or `handler/problem.go`, any two tasks that change `package.json`, `go.mod`, a lockfile, the `Makefile` or migrations, and two frontend tasks that change the same shared files (`app-shell/`, `src/styles/`, `src/test/setup.ts`, `components/ui/`) do not run together. Different directories (`backend/**` against `frontend/**`) usually do.
   - **Blockers for the user:** anything that needs their decision or edit first (the contract, requirements, `STACK.md`, a migration, secrets, deployment details).
   - **Size and risk:** whether it should be split (a task a builder cannot finish in one session, or that mixes a back end and a front end) or merged with a neighbour.
4. **Propose the plan in chat**, and list the backlog disagreements from step 2 with it: the next few tasks to draft, in order, which lane each belongs to (backend, frontend, tooling), which can run at the same time, what each waits for, and what is blocked on the user. Say which items you would leave alone for now and why. Keep it short; the user approves, reorders or overrules it.
5. **Draft in the approved order.** A session may draft several tasks, one at a time: complete steps 1 to 6 for the first before starting the second, and give each its own fresh checker, started right after its file is written (step 5). A task drafted later in the session reads `main` as it is, plus the drafts already written in this session (they are not merged yet; treat them as running tasks when working out conflicts, and name them in "Shared files" and prerequisites). If an earlier answer changes the plan, say so and re-propose it.

The plan is not stored in a file. It would become a second home for backlog items; the next session works it out again from the backlog and `status.sh`.

## Procedure

Steps 1 to 6 are for one task. Repeat them for each task in the plan.

### 1. Read before asking

Before the first question, ground yourself in what exists. A task written against a guess about the code is the commonest source of builder failures.

1. The backlog line, and the requirement IDs it names, in `docs/requirements.md`.
2. The contract for every operation involved: `openapi.yaml`, not only `docs/api.md`. Note parameters, response codes, error codes and descriptions that already settle things.
3. The code on `main` that the task touches, by reading it: names, signatures, interfaces, what is a stub, what already exists. Use `scripts/status.sh --all` and the `docs/tasks/*.report.md` files of the neighbouring tasks to learn what was built and what was left out on purpose.
4. Two or three finished task files of the same side (backend or frontend) and one that is close in shape. They are the best model for depth and tone.
5. The "Known gaps", Non-blocking findings and backlog lines that mention this area. They are either in scope now or must be named as out of scope.
6. For anything that may break: the tests that currently pin the behavior you will change (for example a test that says a stub answers 501). The task must say they are replaced.

Note what runs at the same time: the open tasks and the files they change (`scripts/status.sh`). Name the shared files and who owns each (TEMPLATE, "Role and ownership"). Backend tasks that share `handler/` files or `problem.go`, or any two tasks that change `package.json`, `go.mod`, a lockfile, the `Makefile` or migrations, do not run together; say so and say which must merge first.

### 2. Ask what only the user can decide

Use the question tool when it is available (up to four questions at a time, each with a recommended first option); otherwise ask in plain text. Ask about:

- behavior the requirements and contract do not settle (matching rules, ordering, what happens at an edge);
- which of several designs to build, when the trade-off is theirs (simplicity against polish, now against later);
- anything that needs a change to the contract, requirements, `STACK.md` or a migration;
- the split: what is in this task and what goes back to the backlog.

Do not ask about wording of messages, test names, file names, or a default any careful engineer would pick. Decide those, and list them (step 5).

If the user's answers contradict each other or the contract, say so and ask again; do not pick silently.

### 3. Write the file

Start from `docs/tasks/TEMPLATE.md`. Keep its section order. Delete its guidance comments, its checklist and any section that does not apply. The slug is the file name and is what `stage.sh` takes as `TASK=`.

What a good file has, learned from the earlier tasks:

- **Goal** says what a user (or the system) can do afterwards, then **Requirements covered** (each one proven by an acceptance criterion) and **Out of scope with a reason for each item**.
- **Prerequisite**, at the top, for anything the builder must find already in place (merged tasks, a regenerated contract, a constant in generated code). It tells the builder to stop and ask if it is missing, not to create it.
- **Role and ownership** names allowed and forbidden paths, and the **shared files**. The builder may change only its plan file under `docs/`.
- **Behavior** is exact: every parameter, every failure with its status and code, every limit with what happens at the limit and one past it, the order checks run in when several can fail, the exact wording of every user-visible message. Decide the wording yourself; invented wording becomes a judgment call the user must review. For anything over time (polling, retries, timers, concurrency) say what happens on each outcome.
- **Known gaps**: what is deliberately not solved, so the builder does not work around it and the verifier does not flag it.
- **Structure**: where the code goes, by `ARCHITECTURE.md`; name the files, hooks and helpers that must exist, and anything that must be shared rather than copied.
- **Dependencies**: only what `STACK.md` lists. Otherwise it is a question for the user (step 2), not a line in the file.
- **Acceptance criteria**: every criterion has a test, and the test would fail if the behavior were removed. Group by unit. Include boundaries and every failure listed above. Say which tests are integration tests and what the builder must report about them.
- **Verifier checks**: rules the diff must obey, how to check a UI behavior by reading code (the verifier has no browser), how to confirm a test really discriminates (break the behavior, see it fail, revert), and a list of inputs to try to break it with.
- **Stop and ask when**, and **Handing back**, adapted to the task (for example, naming what to report about a measured time or a judgment call).

Rules for the text itself:

- Use the names that exist in the repo (functions, files, error codes, CSS classes). Never invent one without saying it is new.
- Do not copy code into the file. Describe the behavior and the shape; the builder writes the code.
- Do not leave "TBD", "as appropriate", "handle errors", or "similar to X" without saying what X's rule is.
- Do not claim a requirement is covered unless an acceptance criterion proves it.
- Keep it to what this task does. Everything else is out of scope or a backlog line.

### 4. Backlog

The backlog's rule: one home per item. In the same commit that adds the task file:

- remove the item's line or table row from `docs/tasks/backlog.md`;
- if part of the item is left out, add one line for the left-out part that names the task it came from (for example "Split from `folder-moves`");
- change nothing else in the backlog. If another line is stale, tell the user.

### 5. Check, fix, then show

**Run the checker immediately.** As soon as a task file is written, in the same turn, spawn the checker for that file. Do not wait to finish the backlog change, to draft the next task, or to report to the user. In a session with several tasks, each task's checker starts the moment its own file is written, not after all the files exist. A checker runs in the background, so you may keep working on the backlog line for that task while it runs, but you do not start the next task's file until its findings are handled (steps 5 and 6 are finished for one task before the next one starts).

**Not ready until checked.** Do not push the branch, and do not tell the user a task is ready, until that task's checker has finished and its findings are handled. If the user asks while a checker is still running, say so. A task file that exists on the branch without a finished check is a draft in progress, not something to build from.

Spawn a **fresh subagent** to check it (the Agent tool). It gets no summary of your conversation, only the path of the draft and read access to the repository; that independence is the point. Give it the brief below, unchanged except for the file name.

> You are reviewing a task file that a builder agent will implement without access to the person who wrote it. Read `CLAUDE.md`, `AGENTS.md`, then the task file `docs/tasks/<slug>.md`. Do not edit any file. Check it against the repository as it is now (`openapi.yaml`, `docs/requirements.md`, the code, the tests, `STACK.md`, `CONVENTIONS.md`, `ARCHITECTURE.md`, `TESTING.md`) and report:
> 1. Contradictions: with the contract, the requirements, the code on `main`, another section of the same file, or `AGENTS.md` ownership rules (a file the task tells the builder to change but forbids it to).
> 2. Claims about the code that are wrong or stale: names, signatures, error codes, existing tests, what is a stub.
> 3. Requirements the file says it covers that no acceptance criterion proves, and acceptance criteria no verifier check or test could confirm.
> 4. Behavior left open that a builder would have to invent: a status or message, a limit or its boundary, an order of checks, a failure path.
> 5. Existing tests or behavior that the change breaks and the file does not mention.
> 6. Anything that cannot be done without a dependency, migration, contract change or edit outside the allowed paths.
> 7. Conflicts with tasks that run at the same time or with the backlog.
> For each finding give: Blocking or Non-blocking, the section of the task file, what the repository says (file and line), and what is wrong. Separate findings that are design decisions for the user from mechanical errors. Do not propose a design; list the question. If there are no findings, say so.

Then:

- **Mechanical errors**: a wrong name, a stale signature, a missing test for a claimed requirement, a typo, a wording gap with an obvious fix. Fix them in the file immediately, without asking, and list each in one line (what and where). The user reads the diff in their editor.
- **Design decisions** (anything where two reasonable answers lead to different software): do not decide. Show the user the finding **word for word**, in the checker's own words, not a summary, so nothing is softened. Ask, then apply the answer.
- **Nothing blocking and nothing to decide**: report that in one line.
- At most **two rounds**. After a fix, you may spawn the checker once more on the changed file. A problem still open after the second round goes to the user as it is.

### 6. Report

After each task, a short message, and after the last one a closing summary of the whole session. For a task: the file path and branch, the one-line summary of the task, the checker's result (fixes you applied, questions that remain), the list of defaults you settled yourself (so the user can review them), anything you noticed outside the task (as backlog lines or for the user), and what the user must do before the task runs (merge the branch, make any contract or `STACK.md` change, run `make generate` and push). Say plainly that nothing was run or tested.

## Things that went wrong before

Keep these in mind; each cost a round.

- Tasks written before a neighbour merged, then wrong about a file or a name. Read `main` at the time you draft, and state prerequisites.
- Two agents changing the same files at once. Name the shared files and the order.
- A message or limit the file did not give, which the builder invented. Write the exact text.
- A contract detail missing (`415`, an error code): the builder cannot edit the contract, so the file must say it is a prerequisite and stop if it is absent.
- Acceptance criteria without a test that could fail. If removing the behavior would not turn a test red, rewrite the criterion.
- Backlog items left behind after their task was drafted, so one thing lived in two places.
- Edits made to docs while the user was still discussing. Wait for the go-ahead.

## Before you finish

For each task, and once for the session:

- [ ] The task files, and the backlog changes, are the only files changed (plus any backlog or doc correction the user approved after the reconcile step).
- [ ] Each drafted item is gone from the backlog; any left-out part is named there with its source task.
- [ ] The closing summary lists the tasks in run order, which lanes they are in, which can run together, what each waits for (merges, contract or `STACK.md` edits, `make generate`), and what the user must do first.
- [ ] Nothing was pushed or announced as ready before its checker finished. The checker was started right after each file was written, not after the whole session's drafts, and ran on the final text; mechanical fixes are applied and listed; its design questions are answered or shown to the user.
- [ ] Every defaults-you-chose item is in your final message.
- [ ] The final message says what the user must do before the task can run.
