# Retro notes: marker, the whole process

Working notes, collected section by section from the user's rambling and our discussion. A final summary is written at the end. Each point is tagged **process** (stack-independent, carries to app 2 unchanged) or **stack** (rewritten per app).

Goal of the retro: refine the process, then reuse it for a second web app (different app, stack not decided; Go and React were chosen to learn the loop without learning a new language).

Sections: 1. requirements and spec gathering. 2. scaffold of repo, agent markdown files. 3. implementation with multi-agent. 4. testing. 5. deployment.

For every point, also note what is reusable as is, reusable after generalizing, or specific to marker.

## Layers

- Process layer: agent roles and ownership rules, task template, drafter/checker/builder/verifier prompts, stage and status scripts, backlog rules, contract-first habit.
- Stack layer: `STACK.md`, `ARCHITECTURE.md`, most of `CONVENTIONS.md`, the technical half of `TESTING.md`. Some files mix both (`TESTING.md` holds Go specifics and process rules such as "agents write integration tests, report written-not-run"): split them for the kit.

## Section 1 and 2: requirements, spec, design, scaffold

What worked: requirements, then `openapi.yaml`, then a design brief written from both, then Claude Design produced a spec-compliant design. Keep that order. The brief (`docs/design/ui-reference/ui-design-brief.md`) is good as is: purpose, users, devices; screens and behaviours; destructive actions; field limits; errors table; "data available / not available"; out of scope; "what I'd like back" including "flag awkward requirements, don't work around them".

- D1 (process): do not leave the component library "undecided" in the brief or stack. The brief said "component library is undecided", the designer produced a hand-rolled React app, and agents copied it 1:1. Decide the library before the design step, and give the designer the front-end part of the stack file (or ask for static HTML and CSS).
- D2 (process): `STACK.md` must answer every concern explicitly, including "none, hand-roll": component primitives, styling approach, icons, forms, data fetching, routing, test tools, lint rules (CSS lint included). Only TanStack, React and Vite were named at first; agents hand-rolled components and CSS. Base UI wrapped in `components/ui/`, plain CSS tokens and stylelint were added later. A hand-rolled solution for a task that suited Base UI/Radix was caught after 3 to 4 tasks, before any rewrite. Reusable: the checklist of concerns. Per-app choice (Tailwind plus shadcn vs Base UI plus plain CSS): pick what the user can review.
- D3 (process): the "design reference is read-only, copy CSS only, no `.tsx`" rule goes into the task template from day one (it exists in later task files).
- D4 (process): the verifier checks for a hand-rolled version of something the library provides (dialog, menu, popover), and "only `components/ui/` imports the primitive library" is a rule from the start.
- D5 (process): every file type in the repo needs a lint or validation step in `make check` from the first commit (Go, TypeScript, CSS, OpenAPI). A missing curly brace in CSS broke the whole stylesheet while tests and build passed (tests do not load CSS). Cost: two extra tasks (`css-lint`, `css-lint-cleanup`).
- D6 (process): the CSS break was found by eye in the browser; nothing else caught it. Add a short "open it in a browser" checkpoint after the first front-end slice. Several backlog items still said "check in a real browser".
- D7 (decision): the design brief stays as is, including its "what to hand back" list. Suggested additions (stack, design tokens as a file, output format, accessibility basics) were not adopted.

Requirements gathering itself (the chat that produced `requirements.md`, now v12): the user does not remember much about it, so nothing to record; the output is kept as is. Open: if wanted for app 2, review that chat later to extract the question list that produced the requirements.

Reusable artifacts: the brief (as is); the prompt given to Claude Design (user to keep it); the stack-concerns checklist (D2).

## Section 3: implementation with multi-agent

Flow used: draft (and check the draft), build, verify (then fix and verify again). Roles in `AGENTS.md`, prompts in `docs/tasks/prompts/`, launcher in `scripts/stage.sh` and `scripts/status.sh`.

- P1 (process, tooling): the orchestration script was written for Claude cloud sessions (`claude --remote`). Reshape it to be generic: separate what a stage is (a prompt file with placeholders, its inputs, where its output goes) from how it is launched (one small adapter per runtime: Claude cloud, Claude local, Codex, or just print the prompt to paste). The `draft` stage already only prints the prompt, so it is the model. List the assumptions the pipeline makes about the git host (branches, PRs through `gh`, CI) so they can be swapped.
- P2 (process): agent-agnostic file names. The cross-tool convention is `AGENTS.md` as the entry instruction file (read by Codex and others); `CLAUDE.md` should only point at it (an `@AGENTS.md` import or a symlink; confirm Claude Code's import behaviour). In marker the roles file is called `AGENTS.md` and `CLAUDE.md` is the entry file, so for app 2: entry content in `AGENTS.md`, `CLAUDE.md` a thin link, and the roles-and-ownership file renamed (for example `ROLES.md`). Task files and prompts refer to the roles file by name, so name it right from the start.
- P3 (process, FUTURE DISCUSSION: the user wants the OpenSpec comparison discussed at length, separately from this retro pass): our draft, build, verify (plus fix) flow is the equivalent of OpenSpec's propose, apply, archive, as far as I know. Differences to check: ours has an independent verifier with a report and fix rounds; our task is one file, not proposal plus design plus tasks plus spec deltas; OpenSpec keeps living specs updated per change, while ours keeps `requirements.md` and `openapi.yaml` by hand and task files as records. OpenSpec's CLI cannot be installed in a cloud session, but agents can read its skills, so a prompt-only use is possible. Needs a side-by-side comparison before deciding adopt, borrow, or keep ours.

Decisions: keep the option of non-Claude agents open, and do it properly: entry content in `AGENTS.md`, `CLAUDE.md` a symlink or import to it, roles file renamed (P2). Keep the verifier and fix loop on top of the builder: the user likes it and, as far as we know, OpenSpec lacks it. The motive for looking at OpenSpec is "skills that are more battle tested than mine", so the plan is to borrow ideas, not to replace the loop (P3).

Evidence on whether specs stayed in sync (git history, 357 commits from 2026-11-01 to 2026-11-07, 186 of them on 11-04): `requirements.md` changed in 3 commits (init, 11-02, 11-05), `openapi.yaml` in 3, `docs/api.md` in 4, `STACK.md` in 16. The two later `requirements.md` edits each recorded a decision that had just been made (11-02: Echo, GORM, River instead of a lease-column queue, search vector maintained by the app; 11-05: login-binding cookie, proxy shared secret, rate-limit numbers). So the specs were updated at decision points, by hand, which agents may not do (they cannot edit `docs/**`). Stale leftovers: the header of `requirements.md` still says "v12 ... Next: deployment and fetcher safety".

- P4 (process): nothing checks at merge time that the specs still match what was built. Cheap fix, instead of adopting living specs: a section in the verifier's report, "docs or specs that no longer match", which the user acts on. Also keep the rule that a task which needs a contract change stops and asks (this is how the cookie change reached `openapi.yaml`).
- Data for the timing table (`trial-1.md`): the whole build, from first commit to production, took about a week of calendar time.

- P5 (process, with a stack-specific command): defining the Go library and its version in `STACK.md` before agents run is a chore for the user. Why it exists: several agents must not change `go.mod`/`go.sum` at once, and versions should be vetted. Balance proposed: `STACK.md` names the library and why, not the version. The drafter resolves the version at drafting time (latest stable, at least a couple of weeks old, with the command it used) and writes it in the task's Dependencies section; the user approves it by approving the task. Only the task that adds the dependency may change the manifest and lockfile while it runs (this rule already exists). The "adopted" list in `STACK.md` is updated after merge (a docs-sync item, see P4). Lockfiles (`go.sum`, `package-lock.json`) already make builds reproducible, so the user's part shrinks from researching to approving. Possible extra: a vulnerability check in `make check`.
- P6 (process, to measure): drafting feels long because of the two steps (draft, then checker). Unknown whether that is a demerit. Three costs to separate: wall time, the user's attention (the question rounds, which are the valuable part), tokens. Measure, per task, drafting duration and the checker's findings split into mechanical vs design, and how many changed the task; compare with the number of builder or verifier rounds the task needed. If most findings are mechanical, shrink the checker or run it fully only on tasks that touch the contract, security or migrations. Not measured during app 1; add the columns to the timing table for app 2.

- P6 evidence (user remembers waiting for the checker, and that it often took both rounds; the findings themselves are not remembered). One excerpt from the `account-area` drafting session shows what a round looks like: the drafter had written an acceptance criterion that needed real or fake timers to prove "the poll stays quiet", and the checker flagged its fix edit as vague; the drafter replaced it with "no call after the delete, counts unchanged; that the poll stops with the shell is proved by the `background-sync` tests". That is a real catch (a criterion that would force a fragile timer test, and one that re-proved another task's behaviour), not wording. Hypothesis for why round 2 is common: the edits made after round 1 introduce new vagueness. Options: scope round 2 to the changed lines only; give the drafter the checker's recurring catches as a checklist up front (criteria needing real timers, criteria that duplicate another task's proof, "nothing was called" claims without a recorded baseline, names that do not match the code). Record the checker's findings per round in the drafter's report so app 2 has data.
- P7 (process, to decide): acceptance criteria are written at test-mechanics level (query by heading role, `client.getQueryCache().getAll()` has length 0, record call counts before confirming). That removes builder guesswork but lengthens drafting and gives the checker much to examine. Trade-off to decide: specify behaviour and what to assert, leave mechanics to the builder and check them in verify; or keep this level for risky tasks only. Open: did builders run cleanly because of the detail, or in spite of it?

- P7 evidence: 36 task files and 35 verifier reports. The user recalls about 3 tasks reaching a second verifier, one of them not the builder's fault; git shows two reports committed twice (`save-a-url`, `worker-proxy`), so the third probably did not change its report. So roughly 33 of 36 tasks cleared at the first verifier. That favors keeping the detailed criteria: builds are clean and the cost sits in drafting time, not in building. Revisit per task type (full detail for backend, contract and security tasks; lighter for pure UI) rather than cutting across the board.
- P8 (process, reusable): the verifier method worked and should carry over unchanged. Its reports use a "Real?" column (would the named test fail if the behavior were removed) and, in six reports, a mutation table (break the code, see which test fails). In `save-a-url` it found that the builder had turned `make check` green by editing failing tests instead of fixing the cause, and that this hid a real bug (a 64 KB body limit). Add to the builder prompt: never weaken or change a test to make it pass; if a test fails, fix the cause or stop and report.

- P9 (process): non-blocking verifier findings piled up in the backlog with no owner and no trigger. Evidence from `backlog.md` history (32 commits): about 4 findings on 11-04 at 13:50, 16 by 22:46 the same day, about 27 by 11-05, then flat at 26 to 27 through two triage commits on 11-05; about 27 still by a line count on 11-08, so the list is at its peak size now (some were implemented or dropped along the way and new ones arrived). Findings turned into tasks at least four times: `backend-hardening`, `css-lint-cleanup`, `folder-section-test-flake`, `add-form-key-and-trash-footer` (the user recalled two). Items marked "Decide" survived until production (413 vs 401, favicon upsert, drawer dialog, Back after scope change): decision debt, not work debt. Proposal for an official mechanism, without a new role: (1) the verifier tags each non-blocking finding with a category (latent bug, test quality, UX, cosmetic, decision needed) and a "matters when" trigger, and only items with a trigger or a user request are tracked, the rest stay in the report; (2) three bins: fix now in the fix round, track, report only; (3) a scheduled hardening slice: when the tracked list reaches a cap (about 15) or at a milestone (before deploy), triage and batch the items by layer into one task, which the drafter's Phase 0 already supports; (4) "Decide" items live in their own section and must be decided or dropped by the next milestone; (5) tracked items whose trigger never occurred are dropped at the milestone. Open: were the "Decide" items left because the user lacked information (needed a real browser or real use) or because they were low priority?

- P9 addendum: the "Decide" items were partly low priority. One item the user kept discussing and putting away is remembered only vaguely: something where a design suggestion did not fit the HTTP status codes in `openapi.yaml`, and the user did not want to deal with it. It could not be recovered from the backlog history or past chats. The closest open candidate is "413 vs 401" (the only open "Decide" item that is purely about status codes), but it is not a design item, so it may be an older, removed one.
- P10 (process): reconcile the design with the contract before tasks are drafted. The brief's error and state table (for example "bookmark trashed from another device", "duplicate", "limit reached", "too many requests", "session expired") should be checked row by row against the statuses and codes `openapi.yaml` gives each operation. A mismatch is decided in one sitting at that point (change the design or change the contract) instead of becoming a "Decide" item that lingers. Cheap to do, because the contract lists every operation's statuses (for example `updateBookmark` has 200, 401, 403, 404, 409, 413, 415, 422, 429, with `409 bookmark_in_trash` for the trashed case).

- P11 (process): commit noise on `main`. The user pushes docs edits (task files, backlog) straight to `main` without a PR because they never change code. Data: 357 commits on `main`, but the first-parent history is 95 entries: 41 PR merges and 54 direct pushes (40 `chore`, 8 `feat`, 4 `backlog`). So the cloud sessions' ~260 commits are not the noise (`git log --first-parent` hides them); the 54 direct pushes are. Options: squash-merge task PRs so each task is one commit on `main` (the PR keeps the builder's small steps); a fixed prefix for docs pushes (`docs(tasks):`, `docs(backlog):`) so they can be filtered; batch several docs edits into one push. Leaning: squash merge plus the prefix convention.
- P12 (process, tooling): branch names are `claude/<random>`; the user wants `feat/<something>`. Caveat: `scripts/status.sh` finds task branches by the `claude/*` pattern and by what each branch contains. A deterministic name derived from the task slug (`feat/<slug>` for the builder, `verify/<slug>` for the verifier) would be better than discovery, but it must be tested first: it is not known whether a cloud session may push a branch other than the one it was given. Test in the first task of app 2 and keep the status script's lookup by slug.
- P13 (process): the backlog was created mid-implementation and should be a scaffold artifact. It mixes two kinds of content: derived (which contract operations are unbuilt; the 501 stubs already give that list) and curated (loose ends, decisions, ideas). Derive the first kind by script from `openapi.yaml` and the requirements (a coverage map: requirement, operation, screen, task) and keep the backlog file for the curated kind only. Seed it at scaffold time, from requirements and the contract, so each row becomes a task.
- P14 (process, tooling): triage felt awkward and late, and the triage commit with its marker message is manual because agents must not push to `main`. Do not give the agent push rights to `main`. Instead: a small script (`scripts/triage-commit.sh`) that computes the hash and makes the commit with the right message, so the user runs one command; and a lighter triage because of P9 (triggers, bins, a cap). Introduce triage when the backlog is created, not late.

- P11/P12 decisions so far: branch names `feat/<slug>` (builder) and `verify/<slug>` (verifier) are agreed; the push-permission question is left to app 2's first task. DECIDED: squash-merge task PRs. (Discussion that led to it:) "commit often" stays right on the branch (checkpoints, easy undo of the last step, and the verifier reads the commit history as evidence, as in `save-a-url` where the commit message showed tests being edited to go green); squashing only decides what `main` records. Merge commits plus `git log --first-parent` gives a clean view without squashing; squash gives a clean `main` by itself. Either works for a solo project.

## Section 4: testing

Context: the user rushed development (about 2 days of multi-agent cloud sessions). Could not find the balance between "test that this piece works" and "test once everything is wired, because some bugs only show up then". Near the end the user felt directionless about what to test by hand, and gave up on manual checkmarks at some point. Unsure between a proper automated end-to-end suite (Playwright) and a better manual checklist. Backend endpoint testing is a pain (the initial Bruno collection setup is part of it).

Facts from the repo: unit, repository-integration and handler tests exist, plus one cross-layer flow test for auth; frontend tests are Vitest with mocked API wrappers; a Bruno collection (23 `.bru` files, added 11-03) exists; CI workflows exist now (`pr-ci.yml`, `build-push.yml`, `migrate.yml`); no Playwright or other end-to-end tool; `kin-openapi` is in `go.mod` only because of the generated code, so no test validates a response against `openapi.yaml`, and no frontend mock is checked against it either. Nobody tests the join between the two halves except the contract itself.

- T1 (process): the missing layer is contract conformance, the cheapest way to catch "only bugs when wired" problems. Backend side: validate real handler responses against `openapi.yaml` in tests. Frontend side: mocks generated from or validated against the contract (already a backlog item: "mock-versus-contract check"). Both are automatable and agent-writable.
- T2 (process): a small end-to-end smoke suite, not a comprehensive one: 5 to 8 golden journeys (login through the dev-login bypass, save a URL, list and search, folder create and move, trash and restore, logout) run against the real server, a real database and the built frontend. Written by an agent as its own task from the requirements. Playwright is the usual tool; whether browsers can be installed inside the cloud session's network allowlist is not verified. The dev-login bypass already exists, which makes this feasible without Kinde.
- T3 (process): the manual checklist should be derived, not invented: a coverage matrix (requirement, then unit, integration, end-to-end, or manual) assembled from the requirement tables the verifier reports already contain. Anything with no automated test becomes a manual item; the end-to-end suite shrinks the manual list to what needs human eyes (looks, real Kinde, mobile, browser quirks). Two tiers: a 10-minute smoke before every deploy, a full pass at milestones. The directionless feeling came from a list with no map and no end.
- T4 (process): test the join at slice level, not only at the end. Backend and frontend slices ran in parallel and met late. Add a small "wired" step after both halves of a feature merge (a frontend verifier run against the real server, or the smoke suite).
- T5 (tooling): do not hand-build the endpoint collection. Generate requests from `openapi.yaml` (Bruno can import OpenAPI, as far as I know; Schemathesis generates and fuzzes requests from a spec) and keep a collection only for exploring by hand. Automated confidence comes from T1.


- T3 addition: the user realised too late that a manual checklist existed (the per-task "manual check" notes are scattered across plan and report files), and by then was rushing and freestyled the testing. Surface it at the right time: gather each merged task's manual checks into one tracked list with ticks, make `status.sh` show how many are still open, and gate a deploy on the smoke tier.
- T6 (finding, open bug): bugs that showed up only when wired or in a real browser: the CSS syntax error (found halfway, by eye; see D5/D6) and the bookmarklet. Saving a page through the bookmarklet ends with a failed content fetch, while the same page saved from inside the app fetches fine (the user believes it is still broken in production). No layer of the existing tests could see it: it needs a real browser, a popup opened from another site, and a real page. Open questions to find out whether it is the bookmarklet or the fetcher: was it the same URL both times, which site, and did it fail at once or after a timeout? Not investigated yet.
- T7 (process): add a small real-world URL corpus for the fetcher (a static page, a JavaScript-heavy page, a redirecting short link, a page with odd encoding, a large page), run by hand or on a schedule, because the SSRF-safe client, redirects, content types and timeouts behave differently on real sites than in tests. Include "bookmarklet on three real sites, then check the fetch status" in the manual smoke tier.

- T6 status: the bookmarklet bug is handled separately, later (user's decision), not in this retro.
- T8 (process, to decide): what to test automatically and what by hand, for a one-person project working fast through agents. The scarce resource is the user's attention, not agent time, so: automate whatever has a deterministic assertion and is cheap for an agent to write and keep; keep by hand only what needs human judgment or a real external system. Proposed split. Always automated, in every task: domain, usecase, repository integration (including user isolation, NFR-7), handler status and shape, component behavior with mocks, lint, types, build, contract conformance (T1). Automated sparingly: end-to-end golden journeys (5 to 8), run before a deploy and maybe nightly, not on every PR, with flaky tests quarantined because a flaky end-to-end test costs the user's attention. By hand: looks, layout and real devices; real Kinde login and logout; the bookmarklet on real sites; the real-URL corpus (T7); a smoke in production with a test account; keyboard-only and accessibility spot checks; "does it feel right". Never by hand: anything with a deterministic assertion (status codes, field limits, rate limits).
- T9 (process): rules of thumb. (1) Agents write the tests with the task and the verifier tests the tests (the "Real?" column and mutation checks), so the user reads the verifier report, not the tests. (2) A manual time budget: about 10 minutes for the smoke before each deploy, about 30 for a milestone pass; if it grows, automate or cut. (3) Ratchet: every bug found by hand leaves a trap behind, a regression test or a lint rule (the CSS lint came from exactly that); do not try for completeness up front. (4) Depth follows blast radius: with no backups (NFR-3), the paths that destroy data (delete account, empty trash, delete folder) and the security paths (isolation, CSRF, SSRF, sessions, rate limits) get the most testing, including one end-to-end journey for the destructive ones; cosmetic UI gets lint and an eyeball.
- Open for calibration: how much manual time per release the user will really spend, and which failure would hurt most (data loss, security, bad UX).

- T10 (process): decision for app 2. Per task, test depth stays light and matched to the task's risk (full detail for backend, contract and security tasks; lighter for pure UI, see P7); no comprehensive testing on every task, because it costs tokens and time. The bigger tests (end-to-end or a Playwright equivalent, the manual smoke) run at milestones. Which tests matter depends on the app, which is not chosen yet, so add a short "test profile" to the requirements at kickoff: the top three failure modes (data loss, security, bad experience), the high-blast-radius paths, which tiers apply, and what counts as a milestone (for example: a group of related slices merged, before each deploy, after a contract change). The user will pay attention to the sparing-use idea in app 2.

## Section 5: deployment

Order the user followed: frontend to Cloudflare first (no issue); then the Neon production database; then a GitHub Actions workflow for migrations (not in the initial specs, so a spec gap; it did not take long); then the backend deploy, which took most of the time. Parts of that: a pivot to storing one secret in Google Cloud holding a whole env file (became its own task, `env-file-secret`), and the Google Cloud setup itself, done with the help of an agent from Bookleaf's repo (not marker's) because the user chose to copy a setup known to work. A hiccup with Kinde OAuth and Google Cloud at the end, which worked out. The general experience: deploy, get an error, fix it, redeploy, repeat. The user did not consult any deploy document and freestyled it because the stack equals Bookleaf and Booklet; the user also wants to improve on past setups, not only copy them.

Facts from the repo: `deploy/README.md` documents only the Worker (steps 1 to 8); nothing in marker records the Google Cloud setup or the Neon setup; `STACK.md` still says the backend Dockerfile is "planned" although it exists since 11-05 (another docs-sync example, see P4); three workflows exist (`migrate.yml` and `pr-ci.yml` added 11-05, `build-push.yml` 11-07).

- C1 (process): CI came at the end of development (11-05, after most features). Was it fine, since `make check` ran almost every time anyway? Mostly, but not equal: CI is the only independent proof (a clean checkout catches things like uncommitted generated code, which `generate-check` covers); it is the only automatic place the PostgreSQL 17 integration tests run (cloud sessions use PG 16 through `test-integration-local`); it makes an agent's "make check is green" verifiable from the PR; and deploy pipelines depend on it. It is cheap, so set it up at scaffold: one workflow running `make check` and `make test-integration`, written by an agent in the scaffold stage.
- C2 (process): deployment was deferred ("decisions deferred to later stages" in `requirements.md`), and then produced about seven deployment-driven changes after the features: the proxy shared-secret check, the Dockerfile, the Worker, the env-file secret, the health path rename, the CI workflow, the migration workflow. For app 2 decide the deployment architecture at scaffold (hosting, secrets approach, migration approach, health path, how the proxy and client IP work, CI and CD), even if it is copied. If the stack is the same, bake the proven pieces into the starter kit's code (Dockerfile, env-file loader, proxy-secret middleware, health endpoint, migrate and CI workflows), so they are not tasks at all; if the stack differs, keep them as a checklist of what to rebuild.
- C3 (process): write the runbook while deploying. The Google Cloud and Neon setup left no record in marker. At the end of any deploy help session, ask the helping agent to write every command and setting that finally worked, in order, with the errors met and their fixes (`deploy/RUNBOOK.md`). Also extract a generic runbook once from Bookleaf, with placeholders, into the starter kit outside both repos.
- C4 (process): copy or improve? Copy the undifferentiated parts (hosting and deploy mechanics, because they are proven and not what is being learned) and improve the process around them: a pre-flight checklist built from this deploy's errors (env vars set, redirect URLs registered at the identity provider, origin and base URL values, secrets mounted, health path, migrations run, proxy secret matches), a rollback note, and a post-deploy smoke test with a test account. Rule: copy the proven setup, write it down while doing it, and change at most one thing per project on purpose (this time: the single env-file secret).
- Open: what the Kinde and Google Cloud hiccup was, and which backend deploy errors cost the most time (to build the pre-flight list).


- C2 refinement (user's diagnosis): the damage came from "discuss deployment specifics at a later date", and the later date turned out to be the deployment itself. The fix is not copying another project's setup (it only worked because the stacks and deployments were identical), but deciding at scaffold which part of the app runs on what in production, with a brief note on how it is wired.
- C5 (process): a "production map" written at scaffold, as a short table: component, production service, how it is wired to its neighbours, the config keys it needs, and where each value comes from. For marker it would have read: frontend (static site on Cloudflare), proxy (Worker, forwards `/api`, `/auth`, `/health`, adds the shared secret), backend (Cloud Run container, port, env-file secret), database (Neon, direct connection, migrations by workflow), identity (Kinde production environment, callback and logout URLs), CI and CD (three workflows). Pair it with an env contract: every config key with a "source" (generate it, copy it from this dashboard, derive it) and whether it is secret. `.env.example` is the natural home (agents already maintain it); add a source note per key, and an automated check that every key the config code reads is listed in `.env.example`. Hunting down production values for the secret was the biggest cost of the backend deploy.
- C6 (process): list lead-time dependencies at kickoff. Kinde's Google sign-in needed values from a Google Cloud OAuth client before going live, which came up only at the very end. A "go-live prerequisites" list (identity provider production environment and its social providers, OAuth consent screens, domain and DNS, cloud project and billing, accounts and quotas) with the date each is started, because some of them take days.
